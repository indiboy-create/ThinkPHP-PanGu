Before

那些年，Composer 包留给我们的坑

Composer 解决了“依赖怎么装”，却没有回答“装完之后怎么活”。下面这些坑，几乎每个 ThinkPHP 项目都踩过。

装完还要搬资源

包里有 JS、CSS 和模板，却要手动拷到 public；升级一次忘一次，线上样式和包版本永远对不上。

配置各写各的

有的读 config，有的拿 env，有的藏在构造函数里；换一个项目，就要重新猜一遍用法。

路由与入口失踪

包装好了，页面却不知道从哪里进；路由要不要复制、前缀是多少，全凭 README 的良心。

后台页面重复造

同一套列表、表单与弹层，在每个项目里复制、改名、再复制，重复劳动堆成了技术债。

发布不可复现

包里带部署脚本、隐藏目录和构建产物，别人装出来的样子，和你本地跑出来的不一定是同一个东西。

能力无法被复用

好用的能力被锁死在单个项目里，换一个项目又要重写。生态没有沉淀，只有无穷的复制粘贴。

Standard

现在：一套能落地的 think-store 标准

think-store-xxx 不是换个名字，而是一份可检查、可安装、可被商店发现的工程契约。

理解商店体系

一个包，一个能力

包名即边界：think-store-xxx 只解决一个明确问题，可被单独安装、单独升级，也可被组合使用。

包内视图与资源

模板放 theme/view，静态资源放 theme/assets，由包内路由输出；主项目不需要复制任何文件到 public。

服务注册与路由

Service 在 boot() 阶段加载路由，配置通过 vendor:publish 发布，前缀与开关集中在一个 config 文件里。

商店入口声明

在 composer.json 的 extra.store.home 声明首页地址，think-store 就能识别它、访问它、在管理页里同步它。

可复现的部署

用 project.json 描述部署映射，由 think-store 按约定同步；安装结果与仓库内容一致。

文档与测试是交付物

README 写清安装、配置、路由与边界；测试覆盖核心路径。没有说明的能力，不进入组件矩阵。

Shape

一个标准包，大致长这样

目录不复杂，难的是每一项都各归其位，并且经得起安装与升级。

think-store-xxx

think-store-xxx/
├─ composer.json      # 包名、依赖与 extra.store.home 入口声明
├─ config/xxx.php     # 路由前缀、开关与业务配置
├─ route/             # 由 Service 在 boot() 阶段加载
├─ src/               # Service、Controller、Model 与支撑类
└─ theme/             # view 模板 + assets 静态资源

这套结构已经在示例、编辑器、象棋与天气四个发布包中跑通。你要做的不是发明新约定，而是把约定执行到位。

Who

我们在找这样的你

不需要头衔，只看你愿不愿意把一件事做完整。

愿意写文档的人

知道 README 不是附属品，而是包的一部分；愿意把安装、配置、路由与边界写清楚。

愿意把包当产品的人

不满足于"能跑"，还在意命名、目录、升级路径与别人装完后的第一眼体验。

愿意长期维护的人

接受版本会变、依赖会老，愿意为兼容与迁移留出余地，而不是发布一次就消失。

熟悉 PHP 8 与 Layui 的人

能用 ThinkPHP 8 写服务与路由，也能用 Layui 把后台页面做得干净、克制、好用。

愿意先装一遍的人

发布前把包装进真实项目，验证安装、路由、静态资源与升级路径，而不是只交一份能跑的代码。

愿意接受不同意见的人

命名、目录与边界都可以被讨论；愿意按统一约定迭代，而不是把包当成个人作品。
